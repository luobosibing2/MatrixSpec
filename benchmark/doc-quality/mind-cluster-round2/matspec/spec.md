# mind-cluster-source 规格说明

## 1. 组件定位

### 1.1 核心职责

mind-cluster-source 面向昇腾 NPU 训练与推理集群，负责提供从设备资源发现、NPU 调度、故障诊断、故障恢复到训练运行期容错与 Checkpoint 加速的一体化集群软件能力。

### 1.2 核心输入

1. 集群基础设施：节点、Pod、作业、资源组、调度状态、设备状态和集群拓扑信息
2. 昇腾设备与网络：NPU 健康状态、设备故障、网络故障、DPU/交换机状态、SuperPod 与机架拓扑
3. 训练任务：分布式作业配置、训练进程状态、Rank 信息、恢复状态、Checkpoint 读写请求
4. 运维输入：故障日志、在线拨测结果、人工隔离策略、诊断命令和公共故障上报

### 1.3 核心输出

1. 集群资源视图：可调度 NPU 资源、设备健康状态、节点标签/状态和作业调度结果
2. 故障与恢复结果：作业级故障、故障 Rank、隔离状态、恢复策略、训练停止和恢复信号
3. 诊断结果：离线根因诊断报告、在线网络故障结果、公共故障事件和指标
4. 训练运行期能力：训练任务控制消息、容错状态、Checkpoint 保存/加载结果

### 1.4 职责边界

1. 不负责训练框架本身的模型计算逻辑、优化算法或业务模型正确性。
2. 不负责 Kubernetes、Volcano、昇腾驱动、CANN、硬件设备和底层网络设施自身的安装与运行保障。
3. 不负责替代用户的安全加固策略；组件仅提供必要的权限、输入校验和敏感数据访问约束。
4. 不负责未接入公共故障接口、设备状态接口或诊断输入的数据源的故障判断。
5. 未完整覆盖 Ascend Operator、NPU Exporter、NodeD、Container Manager、Ascend Docker Runtime 的全部外部行为，相关规格待确认。

## 2. 领域术语

**昇腾 NPU 集群**
: 由多个承载昇腾 NPU 的计算节点组成，用于运行训练或推理任务的资源池。

**NPU 设备**
: 集群中可被训练或推理任务申请、调度、挂载和监控的昇腾加速设备。

**设备健康状态**
: 描述 NPU、网络、DPU 或交换机是否可用于作业运行的业务状态。

**作业**
: 用户提交到集群中执行的训练或推理工作负载，可能包含多个副本、多个进程和多个 Rank。

**Rank**
: 分布式训练或推理任务中单个参与进程的逻辑编号，用于定位故障影响范围和恢复动作。

**作业级故障**
: 由设备、节点、网络或公共故障聚合后，对某个作业产生影响的故障视图。

**公共故障**
: 外部诊断系统或在线诊断组件以统一格式上报，并可被集群故障处理链路消费的故障信息。

**人工隔离**
: 当设备在指定时间窗口内达到故障频率阈值后，将其标记为不可继续承载任务的运维控制行为。

**软件故障**
: 同一任务在滑动窗口内多个不同设备出现相同故障码时，被识别为更可能由任务或软件行为导致的故障。
: 软件故障不应直接计入单设备故障频率。

**软切分**
: 将单个物理 NPU 的算力或内存配额划分给多个任务共享使用的资源分配能力。

**多级网络亲和**
: 按 SuperPod、机架、节点等网络层级组织作业任务和集群资源，使任务分配尽量符合网络拓扑亲和要求。

**Checkpoint**
: 训练过程中保存的任务状态数据，用于恢复训练或容错。

**离线诊断**
: 基于用户提供的日志和诊断输入，在任务运行后或故障发生后执行的根因分析能力。

**在线网络故障检测**
: 基于持续采集的网络拨测数据和拓扑信息，对慢网、丢包、延迟或断连等故障进行在线识别的能力。

## 3. 角色与边界

### 3.1 主要角色

1. **训练用户**：提交训练或推理任务，使用 NPU 资源、训练容错和 Checkpoint 能力。
2. **集群运维人员**：部署组件，配置隔离策略，查看资源、故障、诊断报告和恢复状态。
3. **调度系统**：根据作业请求、设备状态和拓扑约束完成 NPU 分配。
4. **训练框架或集成代码**：调用训练运行期接口，接收停止、恢复、热切等控制信号。
5. **诊断使用者**：通过 CLI、SDK 或在线服务获取故障清洗、根因诊断和网络故障结果。
6. **外部故障上报方**：通过公共故障接口向集群上报结构化故障。

### 3.2 外部系统

1. **Kubernetes**：承载节点、Pod、作业状态、资源注册、权限控制和集群状态存储。
2. **Volcano Scheduler**：提供批调度和调度扩展能力，用于承载 NPU 调度策略。
3. **kubelet**：接收节点侧设备资源注册，并在容器启动时请求设备分配。
4. **昇腾驱动与设备管理接口**：提供设备发现、健康状态、网络信息、故障和拓扑能力。
5. **训练框架**：与 Taskd、Mindio TFT、Mindio ACP 集成，执行训练控制和 Checkpoint 读写。
6. **指标与日志系统**：接收运行日志、诊断指标、网络故障指标和运维事件。
7. **公共故障消费者**：订阅或查询集群故障、作业故障和诊断结果的外部系统。

### 3.3 交互边界

mind-cluster-source 通过 Kubernetes、Volcano、gRPC、CLI/SDK、Python API 和文件输入输出与外部系统交互。组件负责把设备状态、调度约束、故障信息和训练运行期信号转化为可调度、可诊断、可恢复的业务结果；外部系统负责提供底层资源、训练业务逻辑、基础设施可用性和必要的权限配置。

## 4. DFX 约束

### 4.1 性能

系统应支持节点侧设备状态周期性刷新、集群故障周期性聚合、训练运行期毫秒级轮询控制和在线网络检测滑窗分析。调度阶段应在每个调度会话内完成作业校验、节点过滤、节点打分和设备分配。在线网络故障检测在滑窗未填满前不得输出告警，避免基于不足样本产生误报。具体规模上限、延迟目标和吞吐指标待确认。

### 4.2 可靠性

设备状态、故障状态、调度状态和人工隔离状态应具备跨进程可恢复的集群级持久状态。节点侧资源注册、集群状态写入、训练网络通信和在线故障上报失败时，应通过重试、周期性刷新、降级或后续全量处理进行补偿。故障恢复链路应避免单次通知丢失导致作业永久无法恢复。Checkpoint 加速不可用时，应尽量降级到普通文件读写或框架原生读写能力。

### 4.3 安全

集群组件应通过服务账号和授权策略限制对节点、Pod、作业、故障和状态对象的访问。包含节点序列号、设备标识、故障码、拓扑、账号凭据或私钥路径的数据应视为运维敏感信息并限制访问。诊断和网络检测文件输入应进行路径、大小、数量和格式校验。Checkpoint 反序列化只应加载可信数据。容器特权、主机路径挂载和运行期共享库加载应按生产安全加固要求收敛风险。

### 4.4 兼容性

系统应保持既有设备状态、人工隔离状态、公共故障格式、作业资源声明、调度注解、诊断结果和训练运行期接口的兼容性。旧版本状态缺少新增隔离原因时，新逻辑应能补齐或兼容读取。离线诊断应兼容历史清洗结果格式。调度插件、调度器和训练运行期共享库必须版本匹配，否则相关能力不可视为可用。生成型公共 API 数据模型变更必须保持与集群运行时注册和默认值逻辑一致。

## 5. 核心能力

### 5.1 NPU 资源发现与上报

**业务规则**

1. **设备发现**：节点侧组件必须发现本节点可用的昇腾 NPU，并向集群上报资源与健康状态。
   - **验收条件**：NPU 节点启动资源上报组件 -> 集群能够看到对应 NPU 资源和节点设备健康状态。

2. **健康变化同步**：当设备健康状态变化时，系统必须更新集群资源视图。
   - **验收条件**：某 NPU 从健康变为故障 -> 后续调度不应继续把新任务分配到该故障设备。

3. **设备分配响应**：当容器启动请求 NPU 资源时，系统应返回对应设备挂载、运行环境和必要资源信息。
   - **验收条件**：任务申请合法 NPU 资源并被调度到节点 -> 容器启动时获得可用 NPU 设备访问能力。

4. **拓扑与附属设备状态**：系统应上报与调度和故障恢复相关的 SuperPod、机架、DPU、交换机和网络状态。
   - **验收条件**：节点具备拓扑和附属设备信息 -> 调度、故障聚合和诊断链路可读取这些状态。

**异常场景**

1. 节点侧参数非法 -> 资源上报组件不得以错误配置继续提供服务。
2. 集群状态写入失败 -> 系统应记录错误，并在后续刷新或重试中补偿。
3. 资源注册失败 -> 节点 NPU 不应被视为可正常调度，直到注册成功。
4. 权限不足导致节点或状态对象无法更新 -> 调度和恢复链路可能缺少输入，应暴露可排障信息。

### 5.2 NPU 作业调度

**业务规则**

1. **作业校验**：系统必须在调度前校验作业的 NPU 数量、软切分、多级网络亲和、SuperPod 和相关调度策略约束。
   - **验收条件**：作业声明不满足 NPU 调度约束 -> 作业不得进入成功分配状态，并应提供不可调度原因。

2. **故障过滤**：调度时必须过滤不可用设备、故障节点和不满足策略的资源。
   - **验收条件**：节点存在影响任务运行的设备故障 -> 新任务不会被分配到该故障资源。

3. **拓扑亲和调度**：当作业声明多级网络亲和时，系统应优先选择符合拓扑层级和资源碎片最优的分配方案。
   - **验收条件**：集群存在多个可行节点组合 -> 系统优先选择更符合网络层级亲和且碎片更低的组合。

4. **设备分配与释放**：作业获得设备后，系统必须更新资源占用；作业释放后，系统必须恢复资源可用视图。
   - **验收条件**：任务完成或被删除 -> 已占用 NPU 资源可再次被其他任务调度。

5. **故障重调度**：当任务受故障影响且满足重调度条件时，系统应尝试基于原有拓扑关系重新分配受影响任务。
   - **验收条件**：作业部分任务因设备故障不可用 -> 系统生成新的调度决策或明确不可重调度原因。

**异常场景**

1. 作业调度策略配置错误 -> 作业校验失败并输出可诊断原因。
2. 节点设备状态缺失或不完整 -> 节点可在过滤阶段被排除。
3. 多级调度层级不连续或任务分组不满足约束 -> 作业校验失败。
4. 调度插件与调度器版本不匹配 -> NPU 调度能力不可视为可用。

### 5.3 软切分资源共享

**业务规则**

1. **资源配额约束**：软切分任务共享同一物理设备时，累计算力和内存配额不得超过设备可用上限。
   - **验收条件**：新任务申请软切分资源后累计配额超过 100% -> 系统拒绝在该设备上分配。

2. **共享策略一致性**：软切分任务只能与共享策略兼容的已有任务共享同一物理设备。
   - **验收条件**：设备已有软切分任务且策略不兼容 -> 新任务不得共享该设备。

3. **优先级策略**：调度应优先选择刚好满足需求、剩余空间更小且策略匹配的设备，以减少资源碎片。
   - **验收条件**：多个设备均可承载软切分任务 -> 系统优先选择资源利用更紧凑的设备。

4. **资源挂载**：软切分任务启动时应获得必要的共享设备配置。
   - **验收条件**：软切分任务成功分配 -> 容器内具备运行所需的共享设备配置。

**异常场景**

1. 节点不存在可用物理芯片或策略兼容芯片 -> 作业不可调度。
2. 软切分目录或资源参数非法 -> 节点侧组件不得继续以错误参数运行。
3. 软切分资源状态缺失 -> 调度应保守拒绝相关分配。

### 5.4 集群故障聚合与恢复

**业务规则**

1. **故障聚合**：系统必须将设备、节点、网络、DPU、交换机和公共故障聚合为作业级故障视图。
   - **验收条件**：某作业使用的设备发生故障 -> 系统产生包含影响作业和故障范围的作业级故障。

2. **固定处理顺序**：故障处理应先完成公共故障、自定义故障、伴随故障、重试、原地恢复、压测过滤、预隔离和增量故障判断，再执行人工隔离。
   - **验收条件**：同一设备同时满足多种故障处理规则 -> 系统按既定优先级输出最终处理结果。

3. **恢复策略协商**：系统应根据故障健康状态、重试能力、故障节点和热切状态选择停止训练、预退出、故障发生、热切等恢复事件。
   - **验收条件**：作业故障进入恢复链路 -> 训练运行期组件收到明确的恢复或停止信号。

4. **订阅通知**：恢复服务、故障查询服务和训练运行期组件应可订阅或查询作业故障。
   - **验收条件**：故障状态变化 -> 订阅方收到更新，查询方可获取当前状态。

5. **周期性补偿**：故障处理必须支持定时全量处理，避免单次事件通知丢失导致状态长期不一致。
   - **验收条件**：某次故障通知丢失 -> 下一轮全量处理仍能识别并处理该故障。

**异常场景**

1. 调度系统客户端不可用 -> 集群故障控制组件启动或相关能力不可用。
2. 恢复服务连接数、请求频率或订阅数超过限制 -> 请求应失败并暴露明确返回状态。
3. 恢复链路缺少必要作业、Pod 或 Rank 信息 -> 系统应保守处理并提供可诊断状态。
4. 人工隔离状态未完成初始化 -> 故障处理不得错误忽略已有隔离状态。

### 5.5 人工隔离

**业务规则**

1. **策略控制**：人工隔离应由集群级策略开关、故障窗口、故障阈值和释放窗口控制。
   - **验收条件**：人工隔离策略被禁用 -> 系统清理隔离判断缓存，不再自动新增隔离设备。

2. **软件故障排除**：同一任务滑动窗口内不同设备出现相同故障码时，应判定为软件故障并排除在设备频率计数之外。
   - **验收条件**：同一任务在多个设备上出现相同故障码 -> 对应故障不触发单设备频率隔离。

3. **频率隔离**：非软件故障在指定窗口内达到阈值后，系统应将设备加入人工隔离状态。
   - **验收条件**：某设备在故障窗口内达到阈值 -> 该设备被标记为隔离，不再作为正常资源调度。

4. **手动删除同步**：运维人员手动删除隔离状态后，系统应在同步周期内更新内部缓存。
   - **验收条件**：隔离状态被人工删除 -> 后续缓存中不再保留该设备隔离记录。

5. **自动释放**：满足无故障时长要求后，隔离设备应支持自动释放。
   - **验收条件**：隔离设备超过释放窗口未再发生相关故障 -> 系统移除隔离状态并记录事件。

**异常场景**

1. 人工隔离策略配置超出合法范围 -> 系统拒绝该配置。
2. 隔离状态存储与内部缓存不一致 -> 同步周期应以明确规则修正差异。
3. 旧版本隔离状态缺少隔离原因 -> 系统应兼容读取并补齐原因。

### 5.6 训练运行期控制与容错

**业务规则**

1. **训练管理初始化**：训练框架或集成代码应能初始化 Manager、Agent、Worker 或 Proxy，并建立任务内控制通道。
   - **验收条件**：训练任务提供合法配置 -> 训练运行期控制组件完成初始化并开始接收控制消息。

2. **恢复信号分发**：当集群故障恢复服务下发信号时，系统应将停止训练、恢复策略、故障 Rank 和恢复状态分发给目标训练进程或控制器。
   - **验收条件**：集群下发停止训练信号 -> 相关训练进程收到停止或回调通知。

3. **状态上报**：训练进程或容错控制器应能上报停止完成、进程故障、恢复策略和恢复状态。
   - **验收条件**：训练侧完成停止或恢复步骤 -> 集群侧可收到对应状态。

4. **消息路由**：任务内消息应支持 Manager、Proxy、Agent、Worker 和控制器之间的分层路由。
   - **验收条件**：目标角色在线且路由可达 -> 消息被送达对应角色。

5. **网络重建**：上游连接异常时，系统应尝试重建任务内网络。
   - **验收条件**：训练运行期连接短暂失败后恢复 -> 系统重新注册并继续收发后续消息。

**异常场景**

1. 训练运行期共享库缺失、版本不匹配或被不安全加载 -> API 初始化失败。
2. 必要环境变量或 Rank 参数缺失 -> 控制器或 Worker 初始化失败。
3. 消息队列满或接收缓冲繁忙 -> 消息入队或接收失败，并返回可判断错误。
4. 网络重建期间 -> 部分消息可能失败，系统应暴露失败状态。

### 5.7 Checkpoint 加速

**业务规则**

1. **透明读写**：训练用户应能通过统一 API 保存、加载、预加载和刷新 Checkpoint。
   - **验收条件**：用户调用保存接口 -> 系统保存训练状态并返回明确结果。

2. **内存文件系统优先**：可用时，系统应优先使用内存文件系统加速 Checkpoint 写入和读取。
   - **验收条件**：加速服务正常运行 -> Checkpoint 写入先进入加速路径，并由后台任务落盘。

3. **异步落盘**：写入完成后，系统应通过后台任务将 Checkpoint 持久化到底层文件系统。
   - **验收条件**：用户调用刷新接口 -> 系统等待后台落盘任务完成或返回失败状态。

4. **降级能力**：加速服务不可用时，保存和加载应尽量降级到普通文件或训练框架原生读写能力。
   - **验收条件**：加速服务不存在且用户调用保存 -> 系统仍尝试通过降级路径完成保存。

5. **可信加载**：Checkpoint 反序列化只应用于可信数据。
   - **验收条件**：用户尝试加载非可信来源 Checkpoint -> 业务上不得将其视为安全操作，安全策略待用户侧确认。

**异常场景**

1. 加速服务不存在 -> 预加载失败，保存和加载可能降级。
2. 刷新时后台任务异常 -> 系统返回失败或未完成状态。
3. 加载目标位置不受支持 -> 加载失败。
4. 异步检查超时时间超出范围 -> 系统拒绝该参数。

### 5.8 离线故障诊断

**业务规则**

1. **日志清洗**：系统应支持用户对训练、推理、设备、主机和自定义日志进行清洗，生成可诊断数据。
   - **验收条件**：用户提供合法输入路径和空输出目录 -> 系统生成清洗结果。

2. **诊断顺序**：训练场景必须先执行根集群诊断，再执行知识图谱、节点异常和网络拥塞等后续诊断。
   - **验收条件**：根集群诊断无法确定待检测设备或故障描述 -> 后续根因诊断终止。

3. **推理诊断**：推理场景应先执行推理相关诊断，再按实例组执行训练侧诊断逻辑。
   - **验收条件**：用户提交推理日志 -> 系统输出推理诊断结果，并对可关联实例组继续分析。

4. **报告输出**：诊断结果应以表格和结构化报告形式输出。
   - **验收条件**：诊断任务成功完成 -> 用户获得包含分析成功状态、故障源、故障链和失败任务信息的报告。

5. **自定义能力**：系统应支持自定义实体、配置或黑名单等诊断辅助信息。
   - **验收条件**：用户配置合法自定义信息 -> 后续清洗或诊断可使用该信息。

**异常场景**

1. 输入路径全部为空 -> 系统拒绝执行清洗或诊断。
2. 非单次诊断场景输出目录非空 -> 系统拒绝覆盖。
3. 知识图谱清洗输入为空 -> 系统返回路径或参数错误。
4. 诊断子任务依赖不可用 -> 系统将其转化为内部错误并在结果中体现。

### 5.9 在线网络故障检测

**业务规则**

1. **检测控制**：系统应支持启动、停止、重载和注册结果回调等在线检测控制命令。
   - **验收条件**：用户发送合法启动命令且配置就绪 -> 在线网络检测开始运行。

2. **拓扑与配置就绪**：检测必须依赖集群拓扑、SuperPod 目录、配置文件和拨测数据。
   - **验收条件**：拓扑或配置未就绪 -> 检测等待或退出，不输出误导性告警。

3. **CSV 拨测处理**：系统应周期性读取拨测结果，过滤早于检测启动时间的数据，并校验文件大小、表头和时间戳。
   - **验收条件**：CSV 文件合法且包含新数据 -> 数据进入滑窗分析。

4. **滑窗告警**：滑窗未填满前不得输出告警；填满后应基于历史均值、标准差和动态阈值识别丢包、延迟和断连。
   - **验收条件**：同一路径连续数据超过动态阈值 -> 系统生成对应网络故障结果。

5. **重复告警抑制**：系统应在抑制周期内避免重复输出同一路径同类告警。
   - **验收条件**：同一故障在抑制周期内持续出现 -> 系统不重复产生等价告警。

6. **公共故障上报**：在线网络故障结果应写入指标并通过公共故障接口上报。
   - **验收条件**：检测产生网络故障结果 -> 指标池和公共故障处理链路可接收到该结果。

**异常场景**

1. 检测根路径未配置 -> 检测控制器退出或无法启动。
2. 超节点目录、配置、拓扑或 CSV 未就绪 -> 检测等待、跳过或失败。
3. CSV 为空、过大、表头错误或时间戳解析失败 -> 对应数据不参与告警。
4. 公共故障上报失败 -> 系统记录失败并保留本地诊断结果。

### 5.10 公共 API 与运维可观测性

**业务规则**

1. **公共作业 API**：系统应提供统一的作业对象、客户端访问和状态订阅能力，供控制器和外部系统使用。
   - **验收条件**：外部控制器使用合法配置访问作业对象 -> 可完成创建、查询、监听或列表操作。

2. **公共故障 API**：系统应提供统一公共故障结构和上报入口。
   - **验收条件**：外部系统上报合法公共故障 -> 故障进入集群故障处理链路。

3. **日志与指标**：组件应输出运行日志、诊断报告、网络故障结果、集群指标和事件，便于排障。
   - **验收条件**：发生资源不上报、作业 Pending、故障未恢复或诊断失败 -> 运维人员可通过日志、状态对象、报告或指标定位原因。

4. **限流与保护**：公共接口应对高频请求、连接数、订阅数和事件输出进行限制。
   - **验收条件**：客户端请求超过限制 -> 系统拒绝或限流，而不影响核心控制面稳定性。

**异常场景**

1. 作业 API 类型未正确安装或注册 -> 外部控制器查询失败。
2. 公共故障格式不合法 -> 上报请求失败。
3. 指标或事件写入失败 -> 系统记录错误并允许后续重试或刷新。
4. 白名单角色之外的客户端注册作业摘要订阅 -> 系统拒绝。

## 6. 数据约束

### 6.1 领域对象

| 对象 | 业务含义 | 关键约束 |
|------|----------|----------|
| 昇腾作业 | 用户提交的训练或推理工作负载 | 必须包含可调度所需的资源、角色、副本和调度信息；状态应反映运行、成功、失败和恢复过程 |
| 节点设备状态 | 某节点上 NPU、网络、DPU、交换机和拓扑的当前视图 | 应保持与节点真实状态尽量一致；健康变化必须可被调度和故障链路消费 |
| NPU 设备 | 可分配给任务的加速资源 | 同一时刻的占用、健康、软切分配额和隔离状态必须一致 |
| 设备故障 | 单个设备或设备关联组件产生的故障 | 必须包含故障类型、级别、故障码、影响范围和处理建议等业务可判断信息 |
| 公共故障 | 外部或在线诊断上报的统一故障 | 必须可被集群故障聚合链路识别，且包含时间、资源、位置、影响和描述 |
| 作业级故障 | 对某个作业产生影响的故障聚合结果 | 应能定位故障 Rank、节点、设备和过滤级别 |
| 人工隔离策略 | 控制自动隔离的运维策略 | 必须包含启用状态、故障窗口、故障阈值和无故障释放窗口；非法配置不得生效 |
| 人工隔离状态 | 被标记为不可正常调度的设备记录 | 应记录节点、设备、故障码、故障级别、隔离时间和隔离原因 |
| 调度请求 | 作业对 NPU 数量、软切分和拓扑亲和的资源声明 | 必须可判定是否合法；非法请求不得进入成功分配状态 |
| 训练运行期消息 | Manager、Agent、Worker、Proxy、控制器之间传递的控制消息 | 必须包含可路由的目标、业务类型、消息类型、返回状态和扩展信息 |
| Checkpoint | 训练状态持久化数据 | 应支持保存、加载、刷新和可选预加载；反序列化数据源必须可信 |
| 离线诊断输入 | 用户提供的日志、配置和自定义实体 | 输入路径必须存在且合法；非单次诊断不得覆盖已有输出目录 |
| 离线诊断报告 | 清洗和诊断后的根因分析结果 | 应包含分析是否成功、故障描述、故障源、故障链、备注和失败任务 |
| 在线拨测数据 | 在线网络检测使用的周期性 CSV 数据 | 文件大小、数量、表头和时间戳必须合法；旧数据不得参与新检测 |
| 在线网络故障结果 | 在线检测输出的网络故障判断 | 应包含任务、时间、源端、目的端、丢包/延迟统计、级别和故障类型 |

### 6.2 状态与生命周期

昇腾作业从提交进入校验和调度阶段，满足资源、拓扑和策略约束后获得 NPU 分配并运行。运行中若设备、节点、网络或公共故障影响作业，系统生成作业级故障并进入恢复链路。恢复链路可能触发停止训练、热切、原地恢复、重调度或失败状态。作业完成、删除或释放资源后，占用的 NPU 应回到可调度状态，除非设备被故障、隔离或健康状态标记为不可用。

NPU 设备的生命周期包括发现、注册、健康上报、分配、占用、释放、故障、隔离和恢复可用。设备健康状态变化应影响后续调度。人工隔离状态可由自动频率判断产生，也可由运维操作删除或由无故障释放规则清除。

Checkpoint 生命周期包括创建、写入、异步落盘、刷新确认、加载和可选预加载。加速路径不可用时，系统可降级到普通读写路径。异步落盘完成前，业务不得假定所有数据已经持久化，除非刷新接口返回成功。

离线诊断生命周期包括输入校验、日志清洗、根集群诊断、后续根因诊断和报告输出。根集群诊断失败时，后续依赖根因边界的诊断不得继续输出确定性结论。

在线网络检测生命周期包括控制启动、配置与拓扑加载、拨测数据扫描、滑窗积累、动态阈值判断、告警抑制、结果输出和公共故障上报。停止或重载时，应清理或重置相关检测状态。

### 6.3 数据质量

资源、故障、隔离、调度和恢复数据应具备可追踪的节点、设备、作业和时间信息。设备状态与调度状态应保持一致，避免同一设备同时被视为可用和隔离。故障码、故障级别、影响范围和故障位置应完整，否则只能作为不完整故障处理或待确认信息。

作业、Rank、节点和设备标识应在各组件间保持一致。公共故障、在线网络故障和离线诊断报告应使用稳定结构，便于测试、订阅和外部系统消费。诊断输入应满足路径合法、格式合法、时效明确和不覆盖已有结果的约束。

敏感数据包括节点序列号、设备标识、故障详情、拓扑信息、账号、密码、私钥和证书路径，应限制访问和日志暴露。Checkpoint 反序列化输入必须可信。运行日志、诊断报告、网络故障结果和人工隔离状态的保留周期在生成设计中未给出，待确认。
