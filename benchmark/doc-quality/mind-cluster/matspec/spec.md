# mind-cluster-source 规格说明

## 1. 组件定位

### 1.1 核心职责

mind-cluster-source 作为仓库级运行时聚合入口，负责对多组件能力进行统一组织、版本协同和交付收敛，确保调度、故障恢复、监控与推理能力在同一运行时闭环内可组合、可追踪、可演进。

### 1.2 核心输入

1. 业务变更输入：[RFC、设计提案、需求说明、兼容性说明]
2. 运行与治理输入：[子组件变更、接口/协议变更、运行事件与告警摘要、指标与审计诉求]

### 1.3 核心输出

1. 下游交付目标：[统一的组件能力边界与版本兼容指引、发布产物清单]
2. 运行治理目标：[可追溯的故障恢复链路说明、监控与审计可观测输出、对外行为约束说明]

### 1.4 职责边界

1. 不直接承担单一业务控制器的完整决策权，如具体调度打分、单任务恢复策略执行、单实例资源分配算法细节。
2. 不负责长期时序数据持久化与离线分析落库；相关历史分析归档交由外部日志或分析系统处理。

## 2. 领域术语

**仓库级聚合运行时**
: 指将调度、故障、监控、推理等子能力以统一契约和统一交付流程组织起来的高阶运行时集合，对外形成一体化行为边界。

**统一契约**
: 指跨组件共享的对象、事件与状态语义，要求版本演进时保持兼容，避免下游组件因字段或语义漂移产生不可预测行为。

**故障闭环**
: 从故障采集、聚合判断、决策下发到恢复/隔离动作回写、审计留痕的完整业务链路。

**人工隔离**
: 运维或策略驱动的设备隔离行为，包含隔离触发、升级、释放与状态回填，要求避免误隔离并可追踪决策依据。

**兼容回填**
: 当历史状态字段发生结构演进时，使用新字段补齐旧状态，保证旧版本数据可被新版本正确识别。

**文档驱动交付**
: 将 RFC、设计、任务、验证与发布说明作为变更有效性前提的治理机制。

## 3. 角色与边界

### 3.1 主要角色

1. **产品与业务方**：定义上层目标、验收边界、发布优先级。
2. **运维与SRE**：关注故障告警、恢复策略、隔离释放、可观测性与审计合规。
3. **开发与交付团队**：在统一约束下交付子组件、维护兼容性与文档一致性。

### 3.2 外部系统

1. **Kubernetes集群平台**：提供统一对象模型与事件机制，是关键状态的最终一致来源。
2. **监控告警系统**：消费指标、告警与可观测事件，支持故障识别与恢复验证。
3. **文档与协作系统**：承载RFC、变更说明、兼容矩阵与发布约束的传播。
4. **持续交付系统**：编译构建、发布打包与版本回退流程的执行环境。

### 3.3 交互边界

组件不实现底层硬件资源具体调配动作，但必须定义并维护可交付的业务边界，确保下游子能力在一致对象语义下联动：从需求输入到恢复/观测输出形成完整可追溯链路。对外可见行为以“可解释的业务结果和事件状态”为核心，不公开实现细节。

## 4. DFX 约束

### 4.1 性能

1. 变更发布与组件构建需支持按组件独立执行，避免单组件故障阻塞其他组件交付。
2. 文档与兼容性更新必须与实现发布同向推进，确保运行方在同一时间窗拿到一致的行为说明。
3. 故障链路关键事件应在可见时间内持续可观测；具体告警响应时延基线待确认（待确认）。

### 4.2 可靠性

1. 关键业务状态以外部状态源为最终一致依据，缓存与临时视图仅作加速，不得成为真相来源。
2. 关键恢复动作与故障状态变更必须幂等可重试，避免重试导致重复恢复或重复隔离。
3. 在配置缺失、外部接口异常、状态读写失败等退化条件下，组件应优先采用保守策略并产生日志与事件，不得掩盖故障。

### 4.3 安全

1. 组件交互默认遵循最小权限原则，避免超范围访问和越权控制。
2. 故障与拓扑数据记录应进行最小化采集，不持久化和输出过量敏感运行时细节。
3. 所有外部输入（配置、阈值、上下文参数）必须经过边界校验；异常值不应直接进入策略执行。
4. 公开文档需同步安全边界（如权限隔离、敏感文件与执行路径风险）并可复核。

### 4.4 兼容性

1. 对外对象语义、接口行为和文档定义的变更必须经过变更治理链路确认并同步更新。
2. 历史状态字段与旧格式兼容策略必须存在，采用非破坏性演进（新增字段、补齐旧字段）而非强制删除。
3. 主要版本兼容边界（受支持环境与协同版本范围）需随版本对外声明；未在声明中的行为变更需标记为待确认。

## 5. 核心能力

### 5.1 文档驱动的变更治理能力

**业务规则**
1. 所有新特性或行为调整必须先形成变更议题并形成跨文件链路，且设计、任务、验证、发布说明需要一致收敛。验收条件：同一变更输入在发布前能在 RFC、设计、任务、验证和发布文档中一一关联到位。
2. 兼容性影响较大的变更必须在发布前披露兼容范围并给出迁移说明。验收条件：发布说明与兼容矩阵包含变更前后可见行为差异。

**异常场景**
1. 变更缺少文档链路时，系统应阻断该版本对外交付。验收条件：构建/发布前被判定为不合规并提示缺失项。

### 5.2 跨组件统一契约与边界收敛能力

**业务规则**
1. 组件间应共享统一对象语义与状态约定，禁止仅由单一组件私有理解造成下游误判。验收条件：同一业务场景在不同组件路径下行为口径一致，且故障事件、状态变更可被其他组件正确识别。
2. 接口行为与对象命名在兼容期内保持稳定，禁止不经说明的破坏性字段移除。验收条件：历史状态在新版本可被正确识别和补齐。

**异常场景**
1. 存在版本不兼容输入时，应回退到兼容映射策略并输出清晰告警。验收条件：任务不因字段缺失即失败，而是可追踪的可用状态继续运行或给出可执行补偿步骤。

### 5.3 故障-恢复闭环协同能力

**业务规则**
1. 故障发生后必须形成可追踪链路：故障采集、升级判定、恢复下发、执行结果、事件留痕。验收条件：任一故障处理都可按时间顺序还原到来源、决策、执行、结果四段。
2. 人工隔离应支持升级与释放流程且具备频率抑制与误隔离风险控制。验收条件：重复或高频故障触发时，系统按预设策略升级处理，同时避免因单次噪声误触发长期隔离。
3. 故障策略冲突或上下文缺失时应走保守策略。验收条件：缺失上下文或策略冲突不会导致无条件强制恢复/隔离，需先降级并提示人工确认。

**异常场景**
1. CM/状态源读取失败或指标缺失时，采用保守回退并生成可见告警；验收条件：不产生“静默成功”，且故障处理链路可继续由人工介入。

### 5.4 按组件独立化的交付与版本管理能力

**业务规则**
1. 发布过程应支持组件独立构建与独立输出，非关键组件故障不应阻断无关组件交付。验收条件：单组件构建失败时，受影响范围可被隔离。
2. 发布必须记录版本与依赖映射，便于回溯和回退。验收条件：每次交付可定位到构成该版本的组件版本关系。

**异常场景**
1. 交付脚本异常时，应支持回滚到可运行基线版本；具体回滚策略与触发条件待确认。验收条件：发生异常时，系统可明确恢复路径并保留最近有效交付记录。

### 5.5 可观测性与审计留痕能力

**业务规则**
1. 关键状态变化（隔离、释放、恢复、策略切换）必须可在监控与事件系统中被业务方观测。验收条件：任一关键动作均有时间、对象、来源、结果可检索记录。
2. 日志应保留链路完整性，即“故障来源-决策模块-执行模块-结果”。验收条件：单次故障可追踪到四段链路信息，支持回溯。

**异常场景**
1. 指标采集源短时失败时仍需保持可观测，允许部分字段降级。验收条件：监控面仍有可用最低指标，不出现整体盲区。

## 6. 数据约束

### 6.1 领域对象

| 对象 | 业务含义 | 关键约束 |
|------|----------|----------|
| AscendJob | 训练类作业的声明与生命周期表达 | 与下游调度、恢复链路保持一致的对象语义，状态变更可观测 |
| 推理服务编排对象 | 推理服务、服务实例与实例集合的分层关系 | 状态收敛规则一致，扩缩与替换行为可预测 |
| 故障事件 | 设备/任务故障的统一记录 | 需带故障来源、时间、影响范围、处理结果 |
| 人工隔离状态 | 人工隔离策略与释放状态的运行记录 | 需兼容历史字段，支持升级与释放闭环 |
| 节点运行状态与指标 | 资源与健康观察基线 | 指标标签需稳定，便于跨系统消费 |
| 发布与兼容元数据 | 版本说明、兼容范围、变更链路说明 | 与实现一致并可追溯到变更输入 |

### 6.2 状态与生命周期

1. 训练与推理工作负载状态需在创建、运行、失败、恢复、完成/终止之间可收敛。
2. 故障事件状态需支持识别、策略评估、动作下发、执行结果四阶段，并保留处理结论。
3. 人工隔离状态应包含“触发-生效-升级-释放”闭环；未能及时释放时需触发再次评估。具体时间窗策略待确认。
4. 发布资产生命周期为“变更输入→设计对齐→验证通过→发布→回滚可选”，每阶段必须有证据可追踪。

### 6.3 数据质量

1. 唯一性：对象按全局标识保持唯一，不得出现同一故障上下文重复创建且不可区分的主记录。
2. 完整性：故障与恢复链路至少包含来源、对象、时间、决策、执行结果四类信息。
3. 格式性：外部可见字段需在兼容变更中保留可解析结构，不得因历史字段缺失导致核心链路中断。
4. 时效性：关键状态变化应及时落地并可在监控端可见；具体最长迟滞时限待确认。
5. 保留策略：仓库级层面不持久化长期历史原始时序库，留存策略以外部分析平台为主，并通过文档约定周期与范围。
