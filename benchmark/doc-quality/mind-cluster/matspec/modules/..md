# 设计模块中间文档（Project Root）

## 1. 模块定位与范围

当前仓库为 `mind-cluster-source` 的根模块，属于“汇总型父模块”（fallback module）。该模块并非单一功能组件，而是用于组织并协调多个独立服务组件、通用库、文档体系、脚本与发布流程的统一入口。  

根模块的目标是承载以下能力：

1. 提供统一的仓库级入口和构建说明（README、构建脚本、版本与兼容性信息）。  
2. 聚合多语言实现组件（Go/C++/Python）及其文档。  
3. 提供公共 API 套件（`ascend-common`）并作为上层组件的共享基础。  
4. 提供面向故障恢复、调度、推理服务、指标采集的多组件能力链。  
5. 提供工程化元文件（MatSpec、CLA、PR 模板、pre-commit、仓库配置）。

核心边界定义如下：

- 根模块输出的是“仓库级能力”与“组件集合”，不承担单一控制平面核心逻辑。
- 业务逻辑实现位于各 `component/*` 子模块。
- 工具链与文档工作流位于 `.agents/.claude/.opencode/.gitee` 等目录。

## 6. 关键约束与设计限制

- 技术栈异构：Go、Python、C、C++ 并存，模块构建路径与依赖图跨语言，根模块不可单一语言假设。  
- 根模块无集中业务边界：没有统一 `src/` 主入口，属于“编排/托管+多组件聚合”层；下层组件必须保持可独立构建与发布。  
- 公开 API 契约集中在 `component/ascend-common`，其他组件若直接消费 k8s CRD/客户端需与该模块版本一致。  
- 根 README 显式要求的构建环境：Go 1.21（MindCluster 总体）；故障诊断侧 Python 依赖要求（>=3.7.5、scikit-learn>=1.3.0、pandas>=1.3.5、numpy>=1.21.6,<2.0.0、joblib>=1.2.0,<1.5.0、ply>=3.11）。  
- 兼容性规则集中在文档与版本策略，涉及多组件联动与 API 稳定性，改动需通过文档链路同步。  
- 自动化文档/流程入口较多（MatSpec、CLA、README、RFC、pre-commit），需避免文档与实现脱节。  
- 根模块为 fallback 情况未提供独立源码模块入口，任何模块级设计都应按“按文件/目录为边界”的方式建立依赖关系映射。  

## 7. 与下游设计文档（design.md）衔接建议

- 先对 `component/*` 进行“按组件交付单元”切分，分别输出子模块设计，再返回根模块整合层。  
- 在 design.md 中应将 `ascend-common` 标记为“平台内核依赖模块”，其变更应触发全局兼容性评估。  
- 对于各业务组件，应在 design.md 中补充：
  - 组件入口（main + pkg 入口）
  - 数据平面入口（CRD、RPC、ConfigMap、文件/消息事件）
  - 失败域与恢复域边界（尤其 clusterd/taskd/noded/npu-exporter/mindio）  
- 需补齐跨组件交互图：`ascend-device-plugin -> clusterd -> taskd -> mindio/infer-operator -> volcano/ascend-operator` 的故障与恢复链与普通作业链路。
