# Document Quality Generalization Experiment Design

## Objective

Validate whether MatrixSpec's round two document generation improvements generalize beyond `mind-cluster`.

The experiment compares MatrixSpec round two, CodeWiki community, and DeepWiki across five repositories or repository modules with different shapes. The result should support a bounded claim: whether MatrixSpec is consistently better than DeepWiki on the sampled projects and where it still loses.

## Sample Set

Use five samples with existing CodeWiki community and DeepWiki baseline material under `../codewiki-community/benchmark/gitcode`.

| Sample | Shape | Source Root | Focus |
| --- | --- | --- | --- |
| `mind-cluster` | multi-component platform repository | `repos/mind-cluster` | component planning, build/config operations |
| `RecSDK` | SDK-style repository | `repos/RecSDK` | API usability, onboarding, source grounding |
| `openharmony-arkui-water-flow` | large UI engine submodule | `repos/openharmony/arkui_ace_engine` | module-specific depth for `frameworks/core/components_v2/water_flow` |
| `openharmony-webview-ohos-nweb` | framework integration repository | `repos/openharmony/web_webview` | cross-layer architecture around `ohos_nweb` |
| `openharmony-pasteboard-core` | service repository where DeepWiki previously won | `repos/openharmony/distributeddatamgr_pasteboard` | completeness, build/test/permission details under `services/core` |

This set intentionally includes one previous MatrixSpec success case, one SDK case, two OpenHarmony module-depth cases, and one case where DeepWiki previously beat CodeWiki. It is designed to avoid a result that only proves the `component/*` optimization.

## Inputs

For each sample, collect:

- MatrixSpec round two output generated by `node bin/matspec.js --lang zh generate --runner codex --mode react`.
- CodeWiki community docs copied from `../codewiki-community/benchmark/gitcode/codewiki-docs` or `openharmony-doc-compare/codewiki-small`.
- DeepWiki material copied from `../codewiki-community/benchmark/gitcode/deepwiki-answers` or `openharmony-doc-compare/deepwiki-pages`.
- Source snapshot from the matching local repo path.

MatrixSpec must continue to use CLI runners only. Do not add or use direct LLM API providers in MatrixSpec.

## Output Layout

Create a new experiment root:

```text
benchmark/doc-quality/generalization/
  README.md
  REPORT.md
  <sample>/
    matspec/
    codewiki/
    deepwiki/
    judge/
      prompt.md
      result.md
      result.json
    REPORT.md
```

The existing `benchmark/doc-quality/work/` directory remains ignored and can hold temporary source copies when needed.

## Evaluation Rubric

Use the same 0-100 dimensions as the `mind-cluster-round2` experiment:

- `coverage`
- `source_grounding`
- `module_validity`
- `architecture_clarity`
- `developer_usability`
- `hallucination_control`
- `operational_completeness`

The judge must also provide:

- total score
- ranking
- winner
- evidence-based rationale
- major weaknesses for each tool
- a short note on whether the sample is a fair comparison or has known baseline mismatch

## Judge Protocol

Use Codex CLI as an independent judge in read-only mode.

For every sample, the judge prompt must require bounded source inspection before scoring. The prompt should name a small set of required source regions and documentation files so the judge does not recursively dump the whole repository.

Required sample checkpoints:

- `mind-cluster`: `component/*`, `build/build_all.sh`, `build/build_each.sh`, `build/service_config.ini`, top-level README/docs.
- `RecSDK`: README/docs, API entry points, build/config files, examples or tests.
- `openharmony-arkui-water-flow`: `frameworks/core/components_v2/water_flow` plus adjacent component registration or render pipeline references.
- `openharmony-webview-ohos-nweb`: `ohos_nweb` files plus build/config/test references.
- `openharmony-pasteboard-core`: `services/core`, permission or API layers, build/test references.

If a source checkpoint is missing in the local snapshot, record that in the sample report instead of inventing evidence.

## Reporting

Each sample report includes:

- source root
- baseline doc paths
- MatrixSpec command and run ID
- score table
- winner and ranking
- short finding summary
- concrete failure modes

The aggregate report includes:

- score table across all five samples
- per-dimension average
- MatrixSpec vs DeepWiki win/loss/tie count
- MatrixSpec vs CodeWiki community win/loss/tie count
- list of dimensions where MatrixSpec still loses
- next optimization backlog

## Success Criteria

The experiment is complete when:

- all five samples have MatrixSpec output, baseline docs, judge prompt, judge result JSON, and a sample report
- the aggregate report summarizes all five samples
- `result.json` files parse successfully
- the repository status is clean except ignored temporary work directories

The conclusion must be scoped to the five-sample benchmark. It must not claim universal superiority over DeepWiki unless future larger benchmarks support that.
